# 双卡任务二 256K 压测（2026-09-25）

在 RTX 5060 Ti 16 GiB（CUDA0）与 RTX 5050 Laptop 8 GiB（CUDA1）的 Windows 主机上，分别用 `layer` 和 `tensor` 完成仓库任务二的 256K 工具历史测试。两组使用同一个 `llama-kvmem-server.exe` 构建和相同的输入历史。基础请求加 32 轮工具请求均成功；最终 prompt 为 261,546 token，生成 512 token，合计 262,058 / 262,144 token。最后一轮两组的前缀缓存均命中 253,618 token。

本次使用 `Qwen3.8-27B-UD-Q4_K_M.gguf`、`--device CUDA0,CUDA1`、`--tensor-split 5,1`、Q5_0 主 KV、F16 草稿 KV、MTP 2 与 `snapshots`、`--kvmem-budget 36864`、`--kvmem-gen-reserve 16384`、128-token block、`-b 512 -ub 512`、262,144 context、thinking budget 128、每请求最多生成 512 token。Windows 构建不支持 NVMe tier，因此采用 `--load-mode none`，避免模型 mmap 与长历史缓存共同挤占系统内存。任务二不发送图片，本次未加载视觉头。`KVMEM_TRACE` 未启用。

预填充与生成吞吐从服务端 33 条 `prompt eval time` / `eval time` 计时按 token 数加权计算；因此预填充包含长历史检索、缓存管理和可能的重算开销，不代表模型纯算子首遍吞吐。墙钟时间来自客户端 33 次 SSE 请求耗时之和，不含加载。显存是 `nvidia-smi` 每秒采样的整卡占用峰值，包含同卡其他进程；系统 RAM 是整机可用量，两个实验开始时的可用量并不相同，不能据其最低值直接推断模式自身的 RAM 消耗。

在此任务上，tensor 的生成速度比 layer 高约 27%，但预填充速度低约 14%，全程多耗时约 10%。两卡显存总占用几乎相同，主要差别是 tensor 将约 1.3 GiB 占用从 5050 转到 5060 Ti，使 5060 Ti 的最低剩余显存降至 1,079 MiB；layer 的两卡最低剩余显存分别为 2,425 和 2,833 MiB。当前原生 tensor 路径对 KV 进行分片，没有复制整份历史 KV。tensor 启动日志显示采样器在 `SPLIT_MODE_TENSOR` 下回退到 CPU；这次没有单独量化该回退的影响。对于以装下较大模型为优先目标的这组显卡，当前测试支持继续以 layer 5:1 为默认，tensor 保留为可选模式。

### 同为 5:1，显存为何不同

`--tensor-split 5,1` 在 layer 模式按**整层序号**分配。该模型有 64 个主层、1 个 nextn 层和输出层；实际 CUDA0 获得主层 0–54，CUDA1 获得主层 55–63、nextn 层及输出层。tensor 模式则把每层可分片的权重、KV 和 GDN 状态按张量维度分片，部分张量镜像，分片边界还必须按量化块及注意力头取整。因此 5:1 不是最终显存占用比例，也不保证两模式有相同的卡间分布。

用同参数、`--verbosity 5 --max-rounds 1` 追加的诊断日志给出以下拆解（MiB）：

| 分配阶段或缓冲 | layer CUDA0 / CUDA1 | tensor CUDA0 / CUDA1 | 说明 |
|---|---:|---:|---|
| KV 池规划时整卡占用 | 12,593 / 4,583 | 13,631 / 3,653 | 在大 KV 池分配前，tensor 已向 CUDA0 转移约 1,038 MiB；主要来自权重布局及早期上下文缓冲。 |
| 主 KV 池，53,248 token | 929.5 / 214.5 | 1,001 / 143 | layer 按 13/3 个注意力层；tensor 实际按 7:1 的 KV 分片。 |
| MTP nextn KV 池 | 0 / 208 | 156 / 52 | layer 的 nextn 整层在 CUDA1；tensor 将其分片。 |
| 全程整卡占用峰值 | 13,628 / 5,132 | 14,974 / 3,810 | 差额另含 GDN 状态、计算图缓冲、CUDA 分配开销与采样误差。 |

layer 权重日志明确为 CUDA0 11,454.81 MiB、CUDA1 3,554.39 MiB。tensor 的 `Meta() model buffer size = 12460.41 MiB` **不是两卡总和**：Meta buffer 的公开 `size` 是其物理子缓冲的最大值（`ggml-backend-meta.cpp` 使用 `max`），在此 5:1 分配下对应较大的 CUDA0 分片。它比 layer 的 CUDA0 权重缓冲大约 1,006 MiB，与 KV 池规划阶段的约 1,038 MiB CUDA0 差额相符。日志没有直接打印 Meta 的另一物理子缓冲大小，不能用 12,460 MiB 与 layer 的两卡权重总和相减来声称 tensor 省了 2.5 GiB 模型显存。

GGUF 张量目录可进一步核实 layer 的权重构成：CUDA0 的前 55 个主层恰为 11,454.81 MiB；CUDA1 的后 9 个主层为 2,224.99 MiB，nextn 层 334.75 MiB，`output.weight` 994.63 MiB，合计 3,554.37 MiB（与分配日志只差对齐/舍入）。在 tensor 模式，约 995 MiB 的输出矩阵及约 335 MiB 的 nextn 权重也参与分片，而非全部留在 CUDA1。这两项解释了权重为何净向 CUDA0 转移约 1 GiB；先前 55 层的一部分同时从 CUDA0 分到 CUDA1，所以净变化小于两项总大小。

此模型每个注意力层只有 4 个 KV 头，5:1 必须取整；实际 tensor 主 KV 两卡为 1,001:143 MiB，即 7:1。主 KV 总计两模式均为 1,144 MiB，MTP KV 总计均为 208 MiB；大历史也只在 GPU 保留 53,248-token 工作池，其余由 KVMem 主机存储。故本次显存差别是**分配位置**，不是 tensor 把完整 256K KV 在两卡各复制一份。

这里复用了仓库 `scripts/multimodal_canary.py` 的任务二消息生成与最终 token 断言，但不是历史性能表的严格复测。历史推荐配置使用不同量化模型、MTP 3 + ReplaySSM，且即使无图片也加载视觉头；当前 tensor 实现尚不支持 ReplaySSM，所以两组统一改用 MTP 2 + snapshots。不能直接把本表数值与历史单卡 IQ3/IQ4 数值归因到分卡模式。

Windows 复现命令：

```powershell
python scripts/windows/task2-dual-256k.py --split-mode layer --tensor-split 5,1 --load-mode none --kv-dtype q5_0 --budget 36864 --reserve 16384 --output build-layer/task2-256k-layer-q5-largepool
python scripts/windows/task2-dual-256k.py --split-mode tensor --tensor-split 5,1 --load-mode none --kv-dtype q5_0 --budget 36864 --reserve 16384 --output build-layer/task2-256k-tensor-q5-largepool
```

两个输出目录分别保留 `argv.json`、`results.json`、`long-context.json`、`server.log`、`memory.csv` 和 `memory-summary.json`。脚本会在系统可用 RAM 连续三次采样低于 2 GiB 时停止自己启动的服务；这两次正式运行均未触发。运行结束后端口 5099 无监听。
