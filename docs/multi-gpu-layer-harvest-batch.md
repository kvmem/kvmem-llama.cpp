# CUDA layer 双卡捕获读回合批

`harvest_pending` 的原双卡路径在每个微批次后逐张量调用 `ggml_backend_tensor_get`，每次调用都会等待所属 CUDA stream。任务一的稳定请求有 112 次 Q/K 捕获读回，共 143,261,696 字节。

CUDA layer 路径现在按物理 GPU 将捕获张量分组，每张卡复用一块 pinned host 缓冲和一条 D2H stream。图计算完成后，先提交所有异步复制，再逐卡等待；主机处理仍按原捕获顺序执行。没有新增 GPU 暂存，也没有改变 KV 布局或复制字节数。读取失败时回退到原逐张量路径；设置 `KVMEM_MULTI_D2H_BATCH=0` 可以关闭合批。非 CUDA 多卡路径不启用合批。

## 实验工作区中的任务一 A/B（2026-09-25）

两组使用同一构建和 Qwen3.8-27B-UD-Q4_K_M，CUDA layer 4:1，`-c 1024 -b 128 -ub 128`、Q8_0 KV、KVMem budget 384 + gen reserve 128、block 32，关闭 MTP、trace、perf。每组启动新服务，预热两次，再以 `cache_reset=true` 测五次，均为 314 prompt、64 generated token。

| 路径 | 预填充 tok/s，中位数（范围） | 314-token 时间 | 生成 tok/s，中位数 |
|---|---:|---:|---:|
| 旧逐张量读取 | 331.17 (325.93–334.67) | 948.2 ms | 18.84 |
| 新按 GPU 分组 | **351.85** (345.40–357.02) | **892.4 ms** | 18.77 |

合批在这组实验中提高预填充吞吐约 6.2%，生成速度基本不变；五次生成文本均一致。另用超过 512-token KVMem 池的 625-token 输入以及 MTP snapshots 请求做了新旧路径输出一致性检查。这些是实验工作区的历史数据；当前分支的独立回归结果如下。

## 当前分支回归（2026-09-27）

从合入后的 `master` 重建，使用 CUDA 13.2.86、`120a-real`，9 项 Windows 仓库测试全部通过。由于 5060 Ti 上另有服务占用显存，本轮使用 Qwen3.5-0.8B-Q8_0 做功能回归，不能与上面的 27B 性能数字比较。

同一二卡 layer 3:1、Q8_0 KV 下，任务一文本分别在合批开/关时生成 32 token，token ID 完全相同；长提示超过 160-token 工作池并强制检索回填时，分别生成 8 token，token ID 也完全相同。诊断日志分别确认 `mode=batch` 与 `mode=legacy`，且 CUDA0、CUDA1 均参与。

`KVMEM_PERF=1` 可记录每个微批次的整图同步、D2H、主机处理和整块归档时间。该开关本身影响吞吐，不用于正式速度比较。112 次复制 API 调用仍存在；减少的是等待次数，不能把优化描述为“112 次复制变成 4 次”。
